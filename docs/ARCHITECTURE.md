# LUMEN Studio — 架构决策记录

本文件记录实现过程中的重要架构决策，配合 [PROJECT_SPEC.md](PROJECT_SPEC.md) 阅读。
任何影响已有模块的变更都应先在此记录并经确认。

## 1. 分层

```
┌──────────────────────────────────────────────┐
│ desktop/src        React + TS (界面层)        │
│   └ api/           类型安全的 HTTP 客户端      │
├──────────────────────────────────────────────┤
│ desktop/src-tauri  Tauri 2 (桌面运行时)        │
│   ├ 原生对话框      tauri-plugin-dialog        │
│   └ backend.rs     启动/监控/关闭 Python 进程  │
├──────────────────────────────────────────────┤
│ backend/lumen      FastAPI (本地服务层)        │
│   ├ api/v1         路由：只做输入输出转换       │
│   ├ services       业务逻辑                   │
│   ├ db             连接、事务、迁移            │
│   └ core           配置、日志、鉴权            │
├──────────────────────────────────────────────┤
│ SQLite (WAL)       %LOCALAPPDATA%\LUMEN Studio │
└──────────────────────────────────────────────┘
```

## 2. 前后端通信（ADR-001）

- Tauri 在启动时生成一次性随机令牌，以子进程方式启动 Python 后端，
  通过环境变量传入 `LUMEN_TOKEN`、`LUMEN_DATA_DIR`、`LUMEN_ALLOWED_ORIGINS`。
- 后端只允许绑定回环地址（`127.0.0.1` / `::1`），端口为 0（由操作系统随机分配）。
- 后端开始监听后，向 **stdout** 输出一行 JSON 握手消息：
  `{"event": "ready", "port": 52341, "pid": 1234}`。stdout 只用于握手，日志走 stderr 和日志文件。
- 前端通过 Tauri 命令 `backend_status` 获取 `baseUrl` 与令牌，之后直接用 `fetch` 调用 API，
  每个请求携带 `Authorization: Bearer <token>`。
- CORS 只允许 Tauri 的来源（`http://tauri.localhost`、开发服务器 `http://localhost:1420`）。
- 生命周期：
  - 后端监听 stdin，stdin 关闭（Tauri 退出或崩溃）即优雅退出。
  - Windows 下子进程被放入 Job Object（`KILL_ON_JOB_CLOSE`），防止残留进程。

## 3. 数据目录（ADR-002）

- 默认 `%LOCALAPPDATA%\LUMEN Studio\`（而非 `%APPDATA%`）：数据库与以后的缩略图缓存体积可能很大，
  不适合随漫游配置文件同步。
- 结构：`lumen.db`、`logs/backend.log`、`backups/`（迁移前自动备份）。
- 可用 `LUMEN_DATA_DIR` 覆盖。
- 缩略图缓存默认在 `cache/`，可在设置里移到其他磁盘（第 34 节，ADR-031）。

## 4. 数据库迁移（ADR-003）

- 不使用 ORM / Alembic，使用标准库 `sqlite3` 与自写的轻量迁移器：
  - 迁移文件位于 `backend/lumen/db/migrations/NNNN_name.sql`，按编号升序执行。
  - `schema_migrations` 记录版本、名称、SHA-256 校验和与执行时间。
  - 每个迁移在单独事务中执行，失败整体回滚。
  - 已执行迁移的文件被修改 → 拒绝启动（防止静默漂移）。
  - 数据库版本高于程序已知版本 → 拒绝启动（防止旧程序打开新库）。
  - 对已有数据的数据库执行新迁移前，先用 SQLite 备份 API 备份到 `backups/`。
- 每个连接启用 `foreign_keys=ON`、`journal_mode=WAL`、`busy_timeout`。

## 5. 数据模型要点（ADR-004）

- **逻辑资产与物理文件分离**：`media_assets`（一张照片/一段视频）↔ `media_files`（磁盘上的文件）。
  RAW+JPEG 是同一个资产下的两个文件（`file_role` = `primary` / `companion`），XMP 为 `sidecar`。
- **路径存储为"根目录 + 相对路径"**：外接硬盘换盘符或整体移动时只需更新 `storage_roots.path`。
  `storage_roots.volume_serial` 用于将来识别重新接入的硬盘。
- **大小写不敏感的唯一性**：Windows 路径用 `path_key`（`normcase` 后）做唯一约束。
- **根目录不允许嵌套**：避免同一文件被重复索引。
- **元数据按文件存储**（`media_metadata.file_id`），记录提取器名称与版本，便于升级后重新提取。
- 删除存储根目录只删除数据库记录（级联删除其文件记录与任务），**绝不触碰磁盘文件**。
- 注册根目录时在同一事务中创建一个 `scan_storage_root` 待执行任务，供 Phase 2 的扫描器消费。

## 6. 前端（ADR-005）

- Tailwind CSS v4 + shadcn/ui（组件以源码形式放在 `src/components/ui`，`components.json` 保留以便后续用 CLI 添加组件）。
- 国际化：i18next，语言顺序 `zh-CN`（默认）→ `en` → `fr`，语言偏好暂存于 localStorage。
- API 类型由后端 OpenAPI 生成（`npm run gen:api` → `src/api/schema.d.ts`），避免手写类型漂移。
- 纯浏览器开发模式（无 Tauri）下，可通过 `VITE_LUMEN_API_URL` / `VITE_LUMEN_API_TOKEN` 连接独立运行的后端，
  目录选择退化为手动输入路径。仅限开发构建。

## 7. 打包（待 Phase 1 之后完成）

- 正式版用 PyInstaller 将后端打包为 `lumen-backend.exe`，作为 Tauri `externalBin` 随安装包分发。
- 开发模式直接使用 `backend/.venv` 中的 Python 运行 `python -m lumen`。

## 8. 媒体处理流水线（ADR-006，Phase 2）

```
storage_roots ──scan──▶ media_files (pending) ──ingest──▶ assets / metadata / renditions
                 快：只比对大小+mtime          慢：指纹 → 归组 → 元数据 → 缩略图
```

- **扫描**（`library/scan.py`）只读文件系统属性，按 `size + mtime_ns` 判断新增/修改/未变，
  每次扫描递增 `scan_generation`；扫描完整结束后，代数落后的文件标记为 `missing`（不删除）。
  根目录不可达时标记 `offline` 并以不可重试错误结束任务，文件记录不变。
- **入库**（`library/ingest.py`）按批（24 个文件）处理 `ingest_state = 'pending'` 的文件：
  1. 指纹：整文件 xxh3-128（`xxh128:<hex>`），只在内容变化后重算；
  2. 归组：同一目录、同名主干的照片合并为一个资产（RAW 为 `primary`，JPEG/HEIC 为 `companion`
     并作为封面），`.xmp` 为 `sidecar`；视频不在这一步与照片配对（实况照片在写入元数据后配对，见 ADR-017）；
  3. 元数据：ExifTool 常驻进程（`-stay_open`，`-charset filename=utf8` 支持中文路径）一次读一批，
     视频再用 FFprobe 补充编码、帧率、旋转与时长；
  4. 缩略图（长边 400px）与预览图（长边 2048px），JPEG，原子写入。
- **拍摄时间**统一存为本地挂钟时间 `YYYY-MM-DDTHH:MM:SS`：优先 EXIF DateTimeOriginal，
  QuickTime 的 UTC 时间换算为本机时区，都没有时退回文件修改时间。
- **尺寸**存为显示方向（EXIF 方向 5–8、视频旋转 ±90° 时交换宽高）。

## 9. 任务引擎（ADR-007）

- 队列就是 `tasks` 表；`TaskRunner` 在后端进程内用一个线程依次执行任务，任务内部再并行。
- 同类型、同根目录的活动任务去重（重复点"重新扫描"不会排多个任务）。
- 失败按指数退避重试（10s、20s…，最多 `max_attempts` 次）；`PermanentTaskError` 不重试。
- 取消：排队中的任务直接取消；运行中的任务设置 `cancel_requested`，处理器在下一次进度上报时退出。
- 关闭应用：运行中的任务放回队列（不计入尝试次数），下次启动继续。
- 优先级：后台补算任务（AI 索引、地名、画质评分）排在其他任务之后，并在有其他任务排队时让位（见第 33 节，ADR-030）。
- **崩溃恢复**：启动时把残留的 `running` 任务放回队列。入库在处理文件**之前**先把该文件的
  `ingest_attempts` 加一，所以导致进程崩溃的坏文件最多重试 3 次就被标记为 `error`，不会卡住队列。

## 10. 移动、丢失与重复（ADR-008）

- **移动**：新文件的指纹与同一根目录下某个 `missing` 文件相同 → 视为移动，新文件继承原资产
  （评分、收藏、备注保留），旧记录删除。
- **丢失**：文件记录保留并标记 `missing`；资产不删除（硬盘可能重新接入）。
- **重复**：`GET /duplicates` 按指纹列出内容相同的文件，只报告，不自动合并或删除。

## 11. 缩略图缓存与访问（ADR-009）

- 位置：`cache/renditions/<指纹前两位>/<指纹>_t1.jpg|_p1.jpg`；按内容寻址，所以重复文件共用一份，
  文件移动后仍然有效；`_t1/_p1` 中的数字是渲染器版本，算法变化时递增即可整体失效。
- 同一指纹的渲染在进程内加锁，避免并发写同一文件（Windows 上会冲突）。
- 缓存被删除时，接口按需重新生成。
- `<img>` 无法携带请求头，因此**仅**缩略图接口额外接受 `?token=`；URL 带内容版本号 `v=`，
  响应可永久缓存（`Cache-Control: immutable`）。

## 12. 外部工具

- ExifTool、FFmpeg、FFprobe 通过 `PATH` 或 `LUMEN_*_PATH` 查找；缺失时降级运行（不提取照片元数据 /
  不生成视频封面），并在日志中警告。正式安装包将随附这些工具（打包阶段处理）。

## 13. 标签、星级与导入（ADR-010，Phase 3）

- `tags`（`name_key` 小写唯一，大小写不同视为同一标签）+ `media_tags(asset_id, tag_id, source)`，
  `source` 为 `user`（在 LUMEN 中添加）或 `import`（来自文件）。
- 入库时只读读取 `XMP:Rating`/`EXIF:Rating` 与 `XMP:Subject`/`IPTC:Keywords`，包括 RAW 旁边的
  `.xmp`（Lightroom 把 RAW 的星级和关键词写在这里）。一个资产取其所有文件中的最高星级。
- `media_assets.rating_source`：`NULL` 未评级，`import` 来自文件，`user` 在 LUMEN 中设置。
  `user` 星级永远不会被重新导入覆盖。
- 迁移 0003 会把已入库文件标记为重新读取元数据并排队入库任务；指纹和缩略图已缓存，所以很快。

## 14. 全文搜索（ADR-011）

- 视图 `asset_search_source` 是"哪些内容可被搜索"的唯一定义：文件相对路径、来源名称、相机、
  镜头、标签名、备注。`lumen.library.search.reindex_assets` 在资产变化时（入库、编辑标签/备注、
  标签改名/删除）从视图重建对应文档；删除资产由触发器同步删除。
- FTS5 使用 `trigram` 分词，查询用 `LIKE '%词%'`：既支持子串匹配，也支持没有空格分词的中文。
  不足 3 个字符的词（如"西湖"）无法使用三元组索引，退化为对索引表的扫描，仍足够快。
- 多个词之间是"且"的关系；`%` 和 `_` 会被转义。

## 15. 查询接口（ADR-012）

- 列表、全选 id、时间轴统计、地图坐标共用同一个筛选构造器（`services/assets._filters`），
  所以同一组筛选条件在各页面结果一致。
- 游标分页编码了排序方式和排序键；用错排序方式的游标会被拒绝。
- `facets` 统计的是整个图库（不随筛选变化），用于填充筛选下拉框。

## 16. 前端：照片墙、浏览器与地图（ADR-013）

- 照片墙用"等高行"（justified）布局：按宽高比把照片排进行，每行恰好填满宽度，最后一行不拉伸；
  宽高比限制在 0.4–3 之间，避免全景图独占一行。布局是纯函数（`library/layout.ts`），配合虚拟滚动，
  只渲染可见行。
- 筛选条件在图库、时间轴、地图之间共享（`library/state.tsx`）；顶部搜索栏实时更新筛选。
- 时间轴按天分组；跳转到某个月是把列表"锚定"在该月（`date_to` 为下个月），可一键回到最新。
  **2026-11-07 起没有单独的时间轴页**：图库页的“按日期分组”开关（默认开，`localStorage` 的 `lumen.groupByDate`）
  给照片墙加上每天的标题和右侧的年月跳转栏（`components/library/DateRail.tsx`）；按“最近添加”排序时不分组；
  “旧→新”排序时跳转用 `date_from` 锚定在该月开头，并“回到最早”。快捷键改为 Ctrl 1–5（图库、地图、AI 搜索、作品集、整理）。
- 全屏浏览显示 2048px 预览，可用滚轮以鼠标为中心缩放、拖动平移（`viewer/zoom.ts` 纯函数 + `ZoomableImage`）；
  第一次放大时加载全尺寸图：未编辑的 JPEG/PNG 直接用原文件，其余（HEIC、RAW、编辑过的照片）用
  `thumbnail?variant=full`——按编辑配方全尺寸显影、带原图 ICC，按需生成并缓存在缩略图目录（`<digest>[_e<hash>]_f1.jpg`）。
  全尺寸图每张 2–6 MB，总量超过 2 GB 时删除最久未用的（每次打开会刷新修改时间，每次新生成后清理）。
- 原文件和实况片段的 URL 只带内容版本（`rendition_version` 中 `-` 之前的部分，前端 `contentVersion`）：
  编辑只改变缩略图，保存编辑不会让 webview 重新下载视频。
  视频直接播放原文件（`/original` 支持 Range）。
- 地图使用 MapLibre；照片在前端用 Supercluster 聚合，气泡用 HTML 标记显示缩略图，因此离线
  底图不需要字体文件。离线底图来自 `world-atlas`（Natural Earth 1:50m 国界，按需加载）。
- 底图样式是设置项 `map_style`（`dark` 默认 / `liberty` / `bright` / `positron`）：在线时就是 OpenFreeMap
  同名样式（同一域名，CSP 不变）；离线时 `dark` 用深色国界图，其余用浅色国界图。设置页和地图页左下角都能切换；
  切换时用 `map.setStyle()` 原地换底图，视野和照片标记（HTML 元素，不在样式图层里）都保留。
- MapLibre 的 Web Worker 以原始源码（`?raw`）通过 `blob:` URL 启动：MapLibre 默认按自身模块
  路径寻找 worker，打包后会失效；CSP 中对应放开 `worker-src blob:`。
- CSP 中新增 `media-src`（视频）和 `https://tiles.openfreemap.org`（仅在线地图使用）。

## 17. 本地 AI 引擎（ADR-014，Phase 4）

- 首选模型 **SigLIP2 so400m/14 @384**（`google/siglip2-so400m-patch14-384`）：多语言，中文查询无需翻译；
  RTX 4070 SUPER 上 fp16 约占 3.4 GB 显存，首次加载约 13 秒。也可选 SigLIP2 base（更快更小）。
- **OpenCLIP** 作为生态与对照：同一 `Encoder` 接口下的第二个后端，并提供 `lumen.ai.bench` 对照工具。
  小样本测试中，英文查询两者相当，中文查询 OpenCLIP ViT-B/32 的 R@1 只有 0.44（SigLIP2 为 1.0）。
- 依赖可选：`pip install -e .[ai]`（PyTorch CUDA 版从 PyTorch 官方源安装）。未安装时其余功能照常，
  AI 相关接口返回 `ai_not_ready`。
- 模型在进程内按需加载（GPU 可用时 fp16），空闲 `ai_idle_unload_s`（默认 600 秒）后卸载以释放显存。
- 模型文件放在 HuggingFace 标准缓存中，与其他工具共用，不在应用数据目录里重复保存。

## 18. 向量化、搜索与标签（ADR-015）

- 后台任务 `ai_index_assets`：读取已缓存的 400px 缩略图（不再解码原图/RAW），批量编码，
  向量（float16、已归一化）存入 `embeddings(asset_id, model_id)`；入库新文件后自动追加；
  封面内容（指纹）或标签词表版本变化时重算。
- 搜索：内存中的精确余弦检索（10 万张 × 1152 维 ≈ 230 MB），写入后失效重载；可与所有筛选条件叠加。
- **相关度阈值**：SigLIP 的 sigmoid 概率对中文查询几乎都接近 0，不可用作阈值；余弦相似度区分清楚
  （真实匹配约 0.10–0.13，无关照片约 0.03–0.06），因此以余弦 0.075 作为"明显相关"，其余结果
  按需展开（`relevant_count`）。阈值来自少量样本，后续用真实照片库校准。
- **自动标签**：约 50 个中文场景/主体标签，每个用多条英文提示词的平均向量。绝对概率同样不可用，
  改为对全部标签做 softmax（使用模型自身的 logit scale），占比 ≥ 0.25 才打标签（最多 3 个）。
  标签以 `source='ai'` 和置信度写入 `media_tags`；重新标注只替换 AI 标签，不动用户和导入的标签。

## 19. 云端分析（ADR-016）

- 供应商：DeepSeek（OpenAI 兼容的 Chat Completions 接口，标准库实现，无额外依赖）。默认模型
  `deepseek-flash`：据第三方资料，DeepSeek 自 2026 年 8 月起在该模型上支持图片输入（每张图约 384 token），
  官方文档未能直接核实，因此提供"测试连接"实际检测，并在模型拒绝图片时提供"仅文字"降级
  （发送拍摄参数和本地 AI 标签，结果明确标注不是基于画面）。模型 ID 和 API 地址可在设置中修改。
- 隐私：默认关闭；API 密钥存 Windows 凭据管理器（`keyring`）；每次请求先调用 `/preview`
  显示目标主机、模型、缩略图和随附字段，用户确认后前端才调用 `/analyze`（后端要求 `confirmed: true`）；
  图片为缩小副本（长边 640–1024 px）；GPS 默认不发送，需逐次勾选。
- 缓存：按 供应商/模型/提示词版本/语言/选项/照片指纹 计算 `cache_key`，相同请求直接返回结果，不再上传。
- 结果为 Markdown（前端用 react-markdown 渲染，不允许原始 HTML）；"AI 选片"要求先输出一行 JSON
  （最佳与排名），解析后在界面上标出最佳照片。

## 20. 实况照片（ADR-017）

- iPhone 实况照片由一张静态照片（HEIC/JPG）和一段约 1.5–3 秒的 `.MOV` 组成，两者写有相同的
  `ContentIdentifier`（照片在 MakerNotes，视频在 QuickTime Keys）。导入时读取该值存入
  `media_metadata.content_identifier`（迁移 0006）。
- **配对规则**（`library/live.py`）：同一目录内的照片与 `.MOV`，
  两者都有 `ContentIdentifier` 时以是否相等为准；任一方缺少时，要求同名且视频不超过 4 秒。
  "照片"导出会改名并带原版/编辑版（如 `SWDK1197.JPG` ↔ `GYFF2926.MOV`、`SWDKE1197.JPG` ↔ `GYFFE2926.MOV`，
  四个文件同一个 ID）：不同名时只配"同为原版"或"同为编辑版"的一对，与导入顺序无关。
- 配对发生在每批结果写入之后（需要两边的元数据），无论照片或视频谁先导入都会配上。视频成为照片资产的
  `companion`（不新增 `file_role`），资产类型仍为 `photo`，封面与拍摄时间仍以照片为准。
  视频原先若是独立资产：星级（用户设置的优先、取较高者）、收藏、备注、用户/导入标签和位置合并到照片资产，
  AI 标签不合并（它描述的是封面），然后删除该视频资产（向量等随之级联删除）。
- 是否为实况由"存在 `.mov` 的 `companion` 文件"推导，列表返回 `is_live`，详情返回 `motion_file_id`；
  视频片段由 `GET /assets/{id}/motion` 提供（与 `/original` 一样支持 Range 和 `?token=`）。
- 片段为 HEVC，不转码，直接由 WebView2 播放（需系统的 HEVC 视频扩展）；播放失败时只显示静态照片。
- 已有数据：迁移 0006 把 MOV/HEIC/JPG 重新标为待处理，只重读元数据（指纹与缩略图保留），由同一配对逻辑处理。

## 21. 非破坏性编辑（ADR-018，Phase 5）

- **编辑配方**（`develop/recipe.py`）：一张照片的全部调整是一份带版本号的 JSON：
  曝光（EV）、对比度、高光、阴影、白色/黑色色阶、色温、色调、自然饱和度、饱和度、清晰度、锐化、暗角，
  以及几何（顺时针 90° 旋转次数、水平翻转、拉直角度、裁剪框）。几何按"旋转 → 翻转 → 拉直 → 裁剪"的顺序应用，
  裁剪框是相对于旋转、拉直后画面的比例坐标，所以与分辨率无关（预览与将来的全尺寸导出一致）。
  默认值等于"未编辑"；内容哈希对浮点取 4 位小数，"全部为默认"的配方哈希为空串。
- **存储**（迁移 0007）：`edit_history` 只追加，每行一份配方及其哈希；`media_assets.current_edit_id`
  指向生效的一步（`NULL` 为原图）。撤销/重做/点历史只移动指针；在撤销后保存新的一步会删掉被撤销的步骤
  （线性历史，与常见编辑器一致）；每张照片最多保留 100 步。"全部重置"也是一步（配方为默认，显示原图）。
- **显影源文件**：资产的 `primary` 文件（RAW+JPEG 时为 RAW，实况照片为静态照片），不可用时退回封面；
  视频和原文件不可用的照片返回 409 `develop_unavailable`。原文件只读，编辑结果只存在数据库和缓存里。
- **编辑后的缩略图**：`renditions/` 下按"源文件指纹 + 配方哈希"命名（`<digest>_e<hash>_t1.jpg`），
  首次请求时渲染；`rendition_version` 变为 `<指纹>-<哈希前 8 位>`，所以照片墙、时间轴、地图的 URL 随编辑变化。
  撤销回某一步时直接复用该步的缓存。列表与详情返回 `is_edited`，照片墙显示"已编辑"标记。
  编辑过的照片不提供 1:1 原图查看（原图是未编辑的）。AI 向量与云端分析仍基于原图。

## 22. 显影渲染（ADR-019）

- **全部在后端渲染**（`develop/engine.py`，numpy float32 + OpenCV），前端只显示结果：屏幕上看到的与将来导出的
  出自同一份代码，不会因 WebGL 与 numpy 两套实现而不一致。代价是每次调整约 100 ms（1600 px、全部滑块启用；
  只有一两项时更快），前端保持"同时最多一个请求、返回后渲染最新配方"，拖动时不会积压。
- **解码只做一次**：按（路径、修改时间、大小、目标尺寸）缓存最近 6 张解码后的底图（只读数组）。
  JPEG 用 libjpeg 缩小解码；HEIC 经 pillow-heif 解码后缩放；RAW 用 LibRaw 去马赛克（相机白平衡、16 位，
  目标尺寸足够小时用半尺寸解码）。HDR 增益图不参与，按 SDR 处理。
- **调整在编码（sRGB）空间中进行**：按 2.2 幂律，线性光中的增益 g 等价于编码值乘 g^(1/2.2)，
  因此曝光、白平衡与黑白色阶合并为每通道一次仿射运算，无需与线性空间来回转换。
  阴影/高光用模糊后的亮度作局部遮罩（在缩小的图上模糊，速度与半径无关）；清晰度为中间调的局部对比度；
  对比度为以中灰为支点的 S 曲线混合；自然饱和度对低饱和颜色作用更强；暗角按画面椭圆半径平滑过渡。
  拉直时自动放大，保证四角不出现空白。
- **接口**：`POST /assets/{id}/develop/preview` 接受未保存的配方和长边尺寸（256–2560），返回 JPEG，
  `X-Histogram` 头带 64 档 RGB 直方图（前端用 SVG 绘制，不需要 canvas）；CORS 暴露该头。
  保存由前端在停止调整约 0.6 秒后（松开滑块后 0.15 秒）发出，离开显影或切换照片时立即保存未保存的修改。
- 依赖：新增 `opencv-python-headless`（SPEC 技术栈中已列出 OpenCV）。

## 23. 导出与批量调整（ADR-020）

- **导出是后台任务**（`export_assets`，`library/exports.py`）：把每张照片按其当前编辑配方全尺寸显影
  （不进底图缓存，避免大图占满内存；指定长边时只按裁剪后够用的尺寸解码），再缩放、写成新的 JPEG。
  原文件只读；导出文件名沿用原文件名（RAW+JPEG 取 RAW 的名字），**已存在的文件绝不覆盖**——
  先用 `O_EXCL` 占用一个空闲名称（`IMG_0001 (2).jpg`），写入同目录临时文件后再替换占位。
  视频和原文件不可用的照片跳过；单张失败记录后继续，全部失败才算任务失败。
- **颜色**：显影在原图的色彩空间里进行（iPhone 为 Display P3），导出时写入原图的 ICC 配置文件；RAW 显影为 sRGB。
- **元数据**：默认用 ExifTool 从原图复制 EXIF/XMP/IPTC（`-TagsFromFile … -all:all`），并修正方向为 1、
  图像尺寸、删除内嵌缩略图；**GPS 默认删除**，每次导出时单独勾选才保留（不记住该选项）。
- **进度与续传**：每张照片后写一次进度；应用重启后任务从已完成的位置继续，不会重复导出。
  任务结果写入 `tasks.result`（迁移 0008，JSON），`GET /exports/{id}` 返回进度和结果
  （导出数量、跳过数量、失败列表）。导出任务不与其他导出合并（`enqueue(unique=False)`）。
- **批量调整**：`POST /edits/batch` 接受一份配方和要采用的字段列表，对每张照片在其当前编辑上覆盖这些字段并
  新增一步历史（已相同则不变）。"拷贝/粘贴设置"只带色调、色彩、细节、效果，不带旋转、翻转、裁剪；
  预设（内置 8 个，定义在前端 `presets.ts`）只设置它列出的值，其余调整保留。

## 24. 视频基础处理（ADR-021）

- **视频配方**（`VideoRecipe`，与照片配方同存 `edit_history`，以 `"kind": "video"` 区分）：保留的起止时间（毫秒，
  终点为空表示到结尾）、额外的顺时针 90° 旋转次数、是否静音。原文件只读，`is_edited`、`rendition_version`
  与照片一致；编辑后的缩略图是原缩略图按旋转转过的副本（只有剪辑或静音时直接用原缩略图）。
  接口：`GET/PUT /assets/{id}/video-edit`（终点超过时长视为"到结尾"，起点超过时长报 400）。
- **播放**：前端 `TrimmedVideo` 只播放保留部分、静音、用 CSS 旋转画面（竖向时交换宽高）；原生控件会随画面旋转，
  所以使用自己的播放/拖动条（浏览模式只覆盖保留部分，编辑模式覆盖全片并标出保留部分）。
- **导出**（同一个导出任务和对话框）：
  - "保持原画质"：`-c copy`，容器与原文件相同，几乎瞬间完成；切点对齐到关键帧（可能早几百毫秒）；
    旋转写入显示矩阵（原有旋转再加上编辑的旋转，`-display_rotation`）。
  - "转为 H.264"：重新编码为 8 位 4:2:0 的 MP4（CRF 20，AAC 192k），切点精确，旋转由 `transpose` 完成。
  - 只取第一路视频和第一路音频（iPhone 文件里的空间音频与数据轨不带走）；元数据用 `-map_metadata 0` 并保留
    QuickTime 键（品牌、型号、拍摄时间），GPS 默认清除（`location`、`com.apple.quicktime.location.ISO6709`）。
  - ffmpeg 无 stdin（`-nostdin`），用 `Popen` 运行，取消或退出应用时会被结束，临时文件删除。
  - 用户库里的视频都是 SDR（bt709）HEVC，因此没有做 HDR 到 SDR 的色调映射；HDR 视频转 H.264 会偏灰（待需要时再做）。
- **导出当前帧**：`POST /assets/{id}/frame-export` 把指定时间的画面（按编辑旋转）存成新 JPEG
  （`<原名>_<分-秒>.jpg`，不覆盖），文件夹沿用上次导出的位置。

## 26. 离线地名（ADR-023）

- **数据**：GeoNames（CC BY 4.0）的人口 1000 以上的地点（约 16 万）、省/大区和国家，只保留中文
  （`zh-CN` > `zh-Hans` > `zh`）和法文名称，英文用 GeoNames 的国际名称。`python -m lumen.geo.build <目录>`
  下载原始数据（`cities1000.zip`、`alternateNamesV2.zip` 约 200 MB 等，只在生成时用）并写出
  `backend/lumen/geo/data/places.tsv.gz`（约 3.6 MB，随程序发布，第一行是数据版本）。运行时完全不联网。
- **去掉以城市命名的城区**："Paris 15 Vaugirard" 这类名字以 25 公里内更大城市开头的地点不收录，
  这些照片归到城市本身。
- **查找**（`geo/places.py`）：没有边界数据，所以按"覆盖半径"选地点：距离除以随人口增长的半径
  （1 000 人约 1.5 公里，200 万人约 19 公里），取最小者；大城市胜过旁边的村子，郊区城镇在自己中心附近仍用自己的名字。
  全部地点的单位向量（float64，float32 下几公里的余弦会被舍入成 1）常驻内存，约 0.4 秒加载，每 700 个点约 1 秒。
- **表**（迁移 0010）：`media_places`（每个有位置的资产一行）保存城市/省/国家的三种语言名称、距离、
  数据版本和所依据的 `media_locations.updated_at`；搜索视图加入全部名称，"巴黎""Paris""Italie"都能搜到。
- **任务** `geo_locate_assets`：导入结束后、以及启动时发现有未命名/位置已变/数据版本不同的资产时排队；
  删除了位置的资产同时删除地名。
- **接口**：资产详情 `place`；筛选 `country`（ISO 代码）/ `place_id`；统计 `places`（国家 → 城市）；
  地图点 `p` + `places`；旅行建议 `cities`/`countries`。前端按界面语言显示（`lib/places.ts`）。

## 27. 数据库备份与恢复（ADR-024）

- **备份**（`services/backups.py`）：用 SQLite 在线备份 API 把 `lumen.db` 复制成一个独立文件，应用照常运行。
  先写 `*.partial`，`PRAGMA quick_check` 通过后再改名，所以不会留下写了一半的备份。内容是全部用户数据
  （评分、标签、备注、编辑、作品集、AI 向量与标签、地名、设置）；缩略图缓存可重建，不备份；
  云端 API 密钥在 Windows 凭据管理器里，不在数据库中。
- **文件名**（本地时间，精确到毫秒，按名称排序即按时间）：`lumen-backup-*`（手动）、`lumen-auto-*`（自动）、
  `lumen-before-restore-*`（恢复前自动另存）；迁移器升级前写的 `lumen-v000N-*` 也列出来，可以恢复。
- **设置**：`backup_auto`（默认开）、`backup_interval_days`（默认 7）、`backup_keep`（默认 10，只删除最旧的
  **自动**备份，其他种类从不删除）、`backup_folder`（默认 `<数据目录>ackups`，建议换到另一块硬盘；
  传空字符串恢复默认）。启动时（以及开启自动备份或更换文件夹时）如果距上一次自动备份已满间隔、且库里有资产，
  就排队 `db_backup` 任务；文件夹不可用时任务失败、不重试，设置页显示"找不到文件夹"。
- **恢复**：可以选列表里的备份，或任意 `.db` 文件（换电脑时）。先只读打开做 `integrity_check`、确认是 LUMEN 数据库、
  用迁移器的 `check_compatible` 拒绝更新版本或被改过的迁移；然后暂停后台任务（`TaskRunner.paused()`，正在运行的
  任务放回队列；15 秒内停不下来就返回 409）、另存一份"恢复前"备份、用备份 API 把备份内容逐页写回正在使用的数据库
  （不重启进程，其他连接之后看到新内容）、运行迁移把旧版本升级到当前版本，再清空内存中的 AI 向量缓存、
  按需排队地名任务。备份相关的四个设置保持恢复前的值（不随备份回退）。前端成功后让全部查询失效重新获取。
- **在资源管理器中显示**：`core/reveal.py` 用 `explorer /select,` 打开（stdin 为 DEVNULL），只接受列表里的备份名。
- 接口：`GET/POST /backups`、`POST /backups/restore`（`name` 或 `path`）、`POST /backups/reveal`。

## 28. 整理：相似照片、废片与淘汰标记（ADR-025）

- **标记**（迁移 0011）：`media_assets.cull_flag` = `none` / `pick`（保留）/ `reject`（淘汰）。淘汰只是标记：
  `AssetQuery.rejected` 默认 `hide`，图库、时间轴、地图、搜索、AI 搜索、统计和旅行建议都不含淘汰的照片；
  `show` 一起显示（瓦片变暗变灰、带标记），`only` 只看淘汰的。作品集照常显示其中的照片。**从不删除文件**：
  `GET /cull/rejected-files` 给出淘汰照片在磁盘上的全部文件（含实况视频、RAW、XMP），前端复制到剪贴板，
  由用户自己决定是否删除。快捷键：图库/全屏中 X 淘汰、P 保留（再按一次取消）。
- **画质**（`library/quality.py`，任务 `quality_score_assets`，导入后及启动时按需运行）：在 2048px 预览图
  （原图的，不含编辑）上测量，结果存 `media_quality`（按封面指纹和方法版本失效）。
  - 清晰度：缩到 1024px，取梯度最强的 0.5% 像素，`|拉普拉斯| 均值 / 梯度均值`——模糊的边缘梯度被摊开，二阶导相对变小。
    没有边缘的画面（纯色墙）记为中性 0.6，不判模糊；长边小于 1600px 的图片（收到/下载的图，因尺寸本身就软）不判模糊。
    在用户库（480 张手机照片）上校准：第 2 百分位 0.28、中位数 0.41，误拍约 0.23，阈值 0.25。
    曾试过整图拉普拉斯方差（把天空等平坦画面误判为模糊）和分块取最清晰区域（漏掉有一处清晰的误拍），都不如现在的方法；
    浅景深特写也可能低于阈值，所以只作为"疑似"让用户确认。
  - 曝光：≥250 的高光和 ≤5 的暗部比例；高光 >35% 且均值 >200 为过曝，暗部 >45% 且均值 <30 为欠曝；PNG（截图、图形）不判曝光。
    带 AI 标签“文档”“截图”的照片（白纸、屏幕本来就亮或暗）只因曝光不会列为疑似废片（用户库上 9 张疑似里有 4 张是这种）。
  - 总分 = 0.7 × 清晰度 + 0.3 × 曝光。
- **相似分组**（`services/cull.py`，按需计算、不存表）：按拍摄时间排序，时间窗口内（默认 10 分钟）SigLIP 向量
  余弦 ≥ 阈值（默认 0.9，界面可选 0.85/0.9/0.95）的照片连成组（并查集）。在用户库上约 79 组 / 187 张。
  每组推荐一张：未淘汰 > 收藏 > 星级 > 编辑过 > 画质分 > 像素数。组里还有未标记的照片就是"待处理"。
  没有向量（本地 AI 未开）时返回 `available: false`。
- **界面**：新页面"整理"（Ctrl 6）——"相似照片"（每组并排，"保留推荐，淘汰其余"/"全部保留"/逐张标记）
  与"疑似废片"（最差的在前）；检查器显示画质与保留/淘汰按钮；多选栏有"淘汰"。

## 29. 重复文件：合并为一张照片（ADR-026）

- **问题**：导入时只把指纹相同、且原来的文件已丢失的新文件当作"移动"；同一内容的两份副本各自成为一张照片，
  在图库里重复出现（用户库副本中 11 组）。
- **分组**（`services/duplicates.py`）：在场（present）、非 XMP 的文件里，指纹相同却属于不同资产的，把这些资产连成组
  （并查集；实况照片的 HEIC 和 MOV 各自重复时仍是同一组）。每组建议保留"用户投入最多"的一份：编辑过 > 标为保留 >
  星级 > 收藏 > 标签数 > 作品集数 > 最早导入。`redundant_bytes` 是其他副本中与保留者内容相同的文件大小。
- **合并**（`POST /duplicates/merge`，只改数据库，**不碰任何文件**）：其余副本的文件改挂到保留的资产上
  （一张照片多个文件位置，数据库本来就支持）；用户数据沿用实况照片配对的 `live.merge_user_data`
  （星级取用户设置的最高者、收藏任一、备注拼接、非 AI 标签合并、位置、作品集位置），另外：保留者没有编辑而副本有时
  把编辑历史移过来（内容相同，编辑照样适用）、云端分析记录、作品集封面；保留/淘汰标记"有一份保留就保留、全部淘汰才淘汰"。
  被并掉的资产删除（向量、画质、地名级联删除，保留者有自己的）。校验每组的资产确实属于同一个重复组，否则 400。
- **之后删除副本**：用户在资源管理器里删掉多余的文件后，重新扫描时 `scan.switch_missing_covers` 把封面换到同一资产里
  仍在场的主文件（优先 JPEG/HEIC/PNG），照片不会变成"丢失"。同一规则也让 RAW+JPEG 中 JPEG 丢失时改用 RAW 显示。
- **界面**：整理页"重复文件"标签：每组列出各副本（星级、收藏、编辑、标签、作品集、全部文件路径、大小、修改时间，
  可"在资源管理器中显示"），可改选保留哪一份；"合并为一张"/"全部合并"。

## 30. 大图库的导入与查询性能（ADR-027）

用户接入 D:（NVMe SSD）和 G:（USB 机械硬盘，8 TB）后图库约 19 万个文件，实测导入 4.5～6 个/秒，
`G:\照片整理` 的 12.6 万个文件预计要 6 小时以上，且越来越慢。原因与改动：

- **实况照片配对全表扫描**：候选查询 `group_key = ? OR m.content_identifier = ?` 跨两张表，SQLite 只能按
  `storage_root_id` 扫描整个来源；每个导入的照片/视频都要查一次（1 万文件 10 ms、2.4 万 17 ms，14 万约 100 ms，
  总量随文件数平方增长，并且在写事务里）。拆成两条走索引的查询（同名：`idx_media_files_group`；
  同 ContentIdentifier：`CROSS JOIN` 固定从 `media_metadata` 的索引开始），每次约 0.01 ms。
  `test_pairing_does_not_scan_the_whole_root` 用 SQLite 虚拟机步数防止回归。
- **导入流水线**：原来每批 24 个文件分"全部算指纹 → ExifTool → 全部渲染 → 保存"四段，每段等最慢的文件，
  读盘时 CPU 闲、渲染时盘闲，且固定 4 线程。现在是滑动窗口（`ingest._run_window`）：每个文件在线程池里独立完成
  指纹、FFprobe、缩略图；窗口 = 线程数 × 3；完成的文件按领取顺序（资产仍按文件顺序创建）每次最多 16 个一起保存
  （一次 ExifTool、一个事务），其间其他文件继续处理。线程数默认 `min(8, CPU/2)`；读文件（指纹）另有闸门：
  机械硬盘或无法判断时 2 个并发（多了只增加寻道），SSD 与线程数相同——用 `IOCTL_STORAGE_QUERY_PROPERTY`
  的 SeekPenalty 判断（`core/volumes.incurs_seek_penalty`）。中断时已领取未完成的文件退回一次尝试次数。
  在 G: 盘实测（同时用户自己的导入也在读这块盘）：JPG 文件夹 16.2 → 33.1 个/秒，HEIC 文件夹 7.8 → 14.9 个/秒。
- **导入期间的界面刷新**：原来每秒刷新来源统计、每 4 秒让所有可见的图库查询失效（统计 0.4～1 s，日志里 1835 次）。
  现在来源统计 5 s，照片墙/时间轴 15 s，其他（统计、地图、相似照片、旅行建议）60 s，结束时全部刷新；
  并以 `dataUpdatedAt` 为触发（任务列表内容不变时也按时刷新）。
- **按写入代数缓存**：`db.connection.transaction()` 提交后递增全局写入代数（恢复备份时也递增），
  `GenerationCache` 把统计、地图点、旅行建议、重复文件缓存到下一次写入。直接写库而不经过 `transaction()`
  的只有任务表和来源状态，不影响这些结果。
- **相似照片**：改用内存中的向量矩阵（`VectorIndex.matrix`，写入后才重载），分组结果按（模型、向量代数、照片数、
  最新照片、窗口、阈值）缓存，标记变化不必重算；只为返回的组（`limit`，默认 60）计算画质与推荐。
- 地图点坐标保留 5 位小数（约 1 米）；打开 AI 搜索页时 `POST /ai/warm-up` 在后台加载模型和向量。

## 31. 外接硬盘断开与重新连接（ADR-028）

原来只在任务开始时检查来源是否可达（`load_root`）。用 `subst` 虚拟盘符模拟导入中途拔盘：剩下的 371 个文件被标成
"丢失"，导入却显示成功、来源显示"就绪"；插回后要手动重新扫描才恢复。扫描中途拔盘同理（遍历跳过读不到的文件夹，
之后把没见到的文件都标为丢失，已导入的照片会暂时从图库消失）。改动：

- **导入**：一组文件里有"找不到"或读失败的，先看来源根目录还在不在；不在就把这组放回队列（不计尝试次数）、
  来源标为 `offline`、任务以 PermanentTaskError 结束，文件状态不变。
- **扫描**：遍历结束后根目录不在了 → `offline`，不标记丢失；遍历中读不到的文件夹/文件（权限、硬盘抖动）
  通过 `walk_media(on_error=…)` 报告，它们下面的文件视为"已见到"（`scan._keep_unreadable`），不会被标为丢失。
- **驱动器监视**（`library/drives.py` 的 `DriveWatcher`，启动时检查一次，之后每 30 秒）：盘符形式的来源用
  `GetLogicalDrives` 判断盘在不在（不访问磁盘，不会唤醒休眠的移动硬盘），每 10 次另外打开文件夹检查一次
  （文件夹被改名/删除）；网络路径每次 `is_dir`。盘没了 → `offline`；离线的盘回来了 → `ready` 并排队扫描
  （恢复以前误标的丢失文件、继续没导完的导入）。
- **换盘符**：离线来源在驱动器列表变化时，按添加来源时记录的卷序列号找现在的盘符，并抽查 8 个已知文件在新位置
  存在且大小一致（同一卷可能出现在多个盘符，例如 subst），通过才把来源路径改过去，原来的照片、评分、编辑都保留。
  `subst` 盘符没有卷序列号，无法这样测试；逻辑由单元测试覆盖，用户的 D:/G: 都有序列号。
- `StorageRoot.is_available` 对盘符路径改为"盘在且状态不是 offline"（原来每次刷新列表都 `isdir`，会碰磁盘）。
- 界面：全屏浏览时原图所在的盘未连接，显示提示（只能看预览，放大原图、播放、显影、导出要等盘接上）；
  来源的"离线"标记有说明（数据都在，插上后自动恢复）。

## 32. 大图库性能第二轮（ADR-029）

在用户库副本（14.5 万项，G: 盘导入中）上测得的剩余瓶颈与改动：

- **导入期间缓存失效**：ADR-027 的写入代数每次导入保存都会增加，导入时统计、旅行建议、重复文件、地图每次都重算
  （日志：统计中位 1.5 s、最高 7 s）。现在分两个计数：用户操作（API 请求里的事务）和后台任务
  （`TaskRunner` 运行任务时 `background_writes()`）。`GenerationCache` 在用户计数变化时立即失效，后台计数变化时
  最多 60 s 才重算；任务结束时记一次用户写入，视图随即刷新。
- **SQLite 内存映射**：每个连接 `PRAGMA mmap_size = 1 GiB`（连接是每个请求新建的，页缓存不能复用；映射走系统文件缓存）。
  时间轴 340 → 110 ms，统计 880 → 380 ms。
- **重复文件**：用户库有 17,458 组（约 104 GB）。`_plan` 只用便宜的列（星级、收藏、编辑、保留标记、标签/作品集数、
  指纹与大小）为全部组排出保留者和多余大小，详细信息（缩略图摘要、路径）只为返回的组生成：4.3 s → 0.29 s。
  迁移 0012 加部分覆盖索引 `idx_media_files_duplicates`。"全部合并"改为后台任务 `merge_duplicates`
  （`POST /duplicates/merge-all`，每 100 组一个事务，状态栏显示进度），不再受一次 1000 组、界面只加载 500 组的限制。
- **AI 索引**：显卡本身约 69 张/秒，原循环串行（解码 → 预处理 → GPU → 保存）只有 42 张/秒。现在模型调用
  （编码和选标签）在一个专用线程上，主循环同时用 4 个线程解码下一批缩略图并保存上一批：本地缩略图实测 43 → 60 张/秒。
- **画质评分并入导入**：导入渲染完预览图后立即测量刚写入的预览文件（还在系统文件缓存里），与原来的独立任务完全相同的算法，
  只对作为封面的文件存结果；独立任务仍会补测其他照片，线程数改为 `ingest_workers`。导入后不再需要单独读一遍全部预览图。
- AI 搜索第一次加载模型时，结果区显示"正在加载 AI 模型，第一次搜索约需 20 秒…"。

## 33. 任务优先级与后台任务让位（ADR-030）

问题（2026-11-05，用户真实日志）：新添加的文件夹 `G:\照片` 一直显示"排队中"，AI 一直显示"正在分析"。原因是队列一次只跑
一个任务、按加入顺序执行，而前一天导入 10 万个文件后自动排了画质评分（8.5 万张）和 AI 索引（13.6 万张，约 40 分钟），
新文件夹的扫描只能排在最后；状态栏又不显示画质评分，AI 在排队时也显示成正在分析。

- **按类型定优先级**（`queue.priority_for`）：`BACKGROUND_KINDS` = AI 索引、地名、画质评分为 0，其余（扫描、导入、导出、
  模型下载、合并重复、备份）为 10。`enqueue` 不传 `priority` 时按类型定；`claim_next` 仍按 `priority DESC, id`。
  旧版本排的任务优先级都是 0，`TaskRunner.start` 用 `apply_priorities` 改正排队中和运行中的任务（不需要迁移）。
- **让位**：后台任务在每次进度上报（约 0.5 s 一次）时检查有没有可以立即运行的更高优先级任务
  （`has_higher_pending`，不算还在重试等待的），有就抛 `TaskYielded`，runner 用 `mark_interrupted` 放回队列
  （不计入尝试次数），先跑插进来的任务，之后再继续。这三个任务都是"查待处理项 → 分批提交"，中途停下不丢已完成的部分；
  重新开始时进度从 0 计，总数是剩下的数量。前台任务之间不让位（导入时导出照旧排队）。
- **界面**：状态栏显示"正在评估画质 x / y"和"正在备份数据库"；没有任务在运行时显示下一个排队的任务（"AI 分析 排队中"）。
  AI 搜索页和设置页区分正在分析、排队中和已停止。
- 日志：任务结束统一记 `task finished`，带 `status`（succeeded / cancelled / interrupted / yielded / failed / error）。
  原来不论结果都记 `task succeeded`。
- 实测（用户库副本）：启动后扫描 `G:\照片` 立即排到 AI 索引前面；AI 索引运行中触发重新扫描 `D:\照片`，1 秒内让位，
  扫描和导入结束后自动继续，尝试次数仍为 1。

## 34. 缓存位置与移动缓存（ADR-031）

问题（2026-11-06）：用户的缓存 109 GB 都在系统盘（C 盘只剩 80 GB）。组成：27.8 万份不同内容各一张 2048 px 预览图
（平均 387 KB，共 102.6 GB）和 400 px 缩略图（6.7 GB），没有残留文件；粗算每多一份内容缓存多 0.4 MB。

- **设置项**：`app_settings.cache_folder`（不在 `AppSettings` 里，只能通过移动缓存来改，因为文件要跟着走）。
  `Settings.cache_folder` 是进程内的当前值，`Settings.cache_dir` 改为普通属性：`cache_folder` 或 `<数据目录>/cache`
  （`default_cache_dir`）。启动时 `services/cache.apply_configured` 读设置；所选文件夹的盘不在时暂用默认文件夹，
  记 WARNING，设置页提示“连接该磁盘后重新启动程序”。环境变量 `LUMEN_CACHE_FOLDER` 也可以指定（数据库设置优先）。
  备份恢复时保留这个设置（`KEPT_ON_RESTORE`）。数据库、日志、备份仍在数据目录。
- **移动**：`POST /cache/move {folder}` 检查（绝对路径、不同于当前、不在当前缓存内、盘存在、可写；盘根目录自动加
  `LUMEN Studio\cache`；跨盘时剩余空间 ≥ 缓存大小 + 5 GB，否则 `cache_move_failed` 带 `needed_bytes`/`free_bytes`；
  同时只能有一个移动任务），然后排队前台任务 `move_cache`（payload 记 `source`/`target`）：
  1. 复制：4 个线程，每个文件先写 `*.moving` 再改名，大小相同的跳过（可续传）；`copy2` 保留修改时间
     （全尺寸图的 2 GB 上限按时间淘汰）。复制期间照常使用旧文件夹，结束后再补一遍期间新生成的文件。
     同一块盘且目标里没有 `renditions` 时直接改名文件夹。
  2. 切换：写设置（目标就是默认文件夹时删除设置）、改 `settings.cache_folder`，不重启；所有用到缓存的地方
     都是每次请求/每个任务开始时现读 `settings.cache_dir`。任务独占队列，切换时不会有导入在写。
  3. 删除旧文件（切换瞬间生成到旧文件夹、新文件夹里没有的先补复制），删空子文件夹和 `renditions`。
  进度把每个文件算两次（复制、删除），界面显示百分比。关闭程序会中断：重启后已复制的跳过；已切换的只剩删除。
  复制阶段取消会删掉已复制的副本、不切换。目标盘满（ENOSPC / 112）不重试。
- **统计**：`GET /cache` 返回当前/默认/所选文件夹、可用性、按类型（预览图 `_p`、缩略图 `_t`、全尺寸 `_f`、其他）的
  文件数和字节数、所在盘剩余空间。用 `os.scandir`（Windows 上目录列表自带大小），用户的 55.7 万个文件约 1 秒，
  结果记 5 分钟，移动后清空。
- **界面**：设置页“缓存”栏：位置、“更改…”（文件夹选择 → 确认框写明大小和目标）、自定义时“恢复默认”、占用空间、
  剩余空间、进度；状态栏“正在移动缓存 N%”。
- 实测（用户库副本，真实缓存的 8 个子文件夹）：C → D 3.7 GB、17,564 个文件 10 秒；再移回默认 10 秒；
  移动期间图库照常显示，现场生成的缩略图写进新文件夹；设置成不存在的盘后启动，退回默认并提示。

## 35. 作品集封面、地图与路线（ADR-032）

需求（2026-11-07）：作品集能选封面；进入作品集后有单独的地图和路线。

- **封面**：后端早已支持（`cover_asset_id`，必须是作品集里的照片，移出后回到第一张）。`Collection` 新增返回
  `cover_asset_id`（null = 默认第一张）。界面：作品集顶部“封面”按钮打开选择框（全部条目网格，点一张即设，

  就并入，否则开始新的停留点（回到去过的地方是新的停留点）。停留点的代表照片取星级最高、再收藏、再最早的；
  地名取多数照片所在的城镇；`day` 从第一张有位置照片的日期算起。里程是停留点之间的直线距离之和。

- **界面**：作品集顶部“照片 / 地图 / 路线”切换。地图与全局地图同一个组件 `components/map/PhotoMap.tsx`

  按天着色的线（`route` 数据源 + 两个线图层，`styledata`/`idle` 时补加，所以换底图后还在）、带编号和代表照片的
  停留点标记（重叠时合并，标签如 “1, 29” / “3–7”）、线段中点的方向箭头（HTML 标记，按墨卡托坐标算角度并随地图旋转，
  屏幕上短于 70 px 的线段不画）。左侧按天分组的停留点列表，点一项飞过去并在右侧列出这些照片；跨天的停留显示结束日期。

## 36. 不同画质的副本（ADR-033）

问题（2026-11-07）：合并重复文件后时间轴里仍有大量重复（2024 年 8 月 2,086 张里 967 对）。它们不是相同的文件：
`G:\Google 相册20240829`（Google 相册导出，11.7 万项）里的照片被 Google 重新压缩（同尺寸、更小，部分 HEIC 转成 JPG，
实况视频丢失），`G:\照片` 等处还有缩小到 1024/2048 像素的副本。ADR-026 只按内容指纹合并，找不到它们。

- **找出**（`services/duplicates._copy_groups`）：可列出的资产按（拍摄时间到秒、类型、文件名主干）分组——主干去掉扩展名、
  不分大小写、去掉 “ (1)” 这类后缀（“-edited” 等编辑版不算）。**2026-11-07 补充**：同一秒拍的照片里，一个文件名是另一个
  前面加了一段再接分隔符（`_ - 空格 .`）的也算同名——`G:\照片整理` 按日期改过名（`20160101_IMG_1584` 对 Google 的 `IMG_1584`），
  还有 `102APPLE_`、`NEO_IMG_` 前缀；被包含的名字至少 4 个字符。按“同一秒”分桶后用后缀查表合并（线性，不两两比较）。
  编辑版（`IMG_E0546`、`IMG_7592-已修改`）、连拍相邻编号仍然不算。用户库（已合并过一次）又找到 5,048 组、10.2 GB，
  2015–2016 年为主，2016 年上半年 2,146 组。组内按画质排序：像素 > 带实况视频 > 原始格式
  （HEIC/RAW）> 文件大小；每份并入第一个与之相符的更好副本，否则自成一组（同名但另一台相机的照片、裁剪过的版本）。
  相符：相机型号相同（缺失不算不同）、长短边比例相差 ≤ 2 %、视频时长相差 ≤ 1.5 s；**尺寸不同**（缩小过）的还要
  AI 图像向量余弦 ≥ 0.7（两份都有向量时）。用户库副本：同尺寸 98 % 的对 ≥ 0.98，旋转 90° 或只有几十 KB 的真副本低到
  约 0.73，0.48 的那对被排除。向量只读需要比对的（约 6 万个，约 4 秒），相似度按（模型、向量索引代数、两个资产）
  缓存，`VectorIndex.generation()` 在新向量写入或换数据库时变化。表大时（> 2 万个资产）一次扫表代替分批 IN 查询。
- **保留**：画质最好的一份（不像相同文件那样按“用户投入”选）；合并沿用 ADR-026 的 `_merge`：其余副本的文件挂到
  保留的照片下、星级/标签/备注/作品集合并；保留者没有编辑而副本有时把编辑移过来（裁剪是相对比例，同比例的副本适用）。
  不碰任何文件。`redundant_bytes` 是其余副本全部文件的大小。
- **接口**：`GET /duplicates?kind=copies`、`POST /duplicates/merge {kind: "copies", groups}`（校验每组确实是同一组副本）、
  `POST /duplicates/merge-all?kind=copies`（任务 payload 记 `kind`）。默认 `identical`，与以前一样。
- **界面**：整理页“重复文件”上方切换“内容完全相同 / 不同画质的副本”；副本模式每份显示尺寸和格式；首次查找有
  “正在查找…”提示；合并一组后立即从列表去掉，报告在后台重算。
- 实测（用户库副本）：86,370 组、多余 95,341 项、190 GB；首次报告约 10 秒；全部合并 5 分 48 秒；图库 270,347 → 175,006 项，
  2024 年 8 月 2,086 → 1,120 张（剩下的同秒照片是全景图与普通照片、相邻两张，确实不同）。

## 39. Google 相册导出的实况视频（.MP4）配对（ADR-036）

问题（2026-11-07）：2021–2022 年约 1.07 万个 4 秒内的小视频没有和照片合并。Google 相册导出时把实况照片的动态部分
存成 `.MP4`（`IMG_0421.HEIC` + `IMG_0421.MP4`，ContentIdentifier 还在），而 ADR-017 只把 `.MOV` 当实况视频；
合并“不同画质的副本”后，一个视频资产还可能有好几个文件（`.MOV` 与 Google 的 `.MP4`），原规则要求视频只有一个文件。

- **规则**（`library/live.py`）：`CLIP_EXTENSIONS = ("mov", "mp4")`；`.MP4` **只按 ContentIdentifier 相同**配对（不按同名 + 时长，
  避免误配真正的短视频）。视频资产有几个文件时整组并入照片，全部标成 `companion`（sidecar 仍是 sidecar）。
  照片已经有动态部分时，同一 ContentIdentifier 的其他副本也并进来（另一个文件位置），不同编号的不并。仍要求同一文件夹。
- **播放**：`is_live` 与 `motion_file` 认 `.mov`/`.mp4` 两种；有几个副本时取在场的、优先 `.MOV`。
- **补配**：任务 `pair_live_photos`，启动时若 `app_settings.live_pairing_version` < 2 就排队一次：对每个仍属于视频资产、
  有 ContentIdentifier 或 ≤ 4 秒的 `.mov`/`.mp4` 文件跑一次配对，完成后写版本号。状态栏“正在配对实况照片 N / M”。
- 实测（用户库副本）：检查 25,429 个视频文件，配上 10,705 个，16 秒；2021–2022 年单独的小视频 10,692 → 73
  （51 个没有编号的是真短视频，21 个照片只在另一个文件夹里，1 个没有对应照片）。动态部分为 `.MP4` 的照片 `/motion` 返回 `video/mp4`。

## 40. 实况照片玩法：换一帧、长曝光、循环与来回（ADR-037）

需求（2026-11-08）：用实况照片的视频片段做出新照片——选一张更好的帧当照片、把整段叠成长曝光，以及像 iPhone 一样循环 / 来回播放，
并能导出为 MP4 / GIF。原文件只读，一切仍是非破坏性编辑。

- **配方**（`develop/recipe.py`）：`EditRecipe` 增加 `live_frame_ms`（选用的帧，`null` 为原照片）和
  `live_effect`（`live` / `loop` / `bounce` / `long_exposure`）。不需要数据库迁移（配方是 JSON）；这两个字段等于默认值时
  **不进入 `canonical_json`**（`_LATER_FIELDS`），所以已有编辑的哈希和缓存不变。它们属于某一段片段，不在“拷贝/粘贴设置”和
  批量应用的字段里（`RecipeField`）。没有片段的照片保存这两个字段返回 409。
- **片段模块**（`develop/live.py`，不碰数据库）：`probe` 用 ffprobe 读尺寸（按显示旋转换成竖直方向）、每帧时间、色域和
  “原照片的位置”——iPhone 片段里有一条只含一个极短样本的元数据轨，它的 `start_time` 就是拍静态照片的时刻（如 1.433 s）。
  **编辑列表之前的包（负时间戳）不计入**：它们只为解码第一帧而存在、不会输出（`IMG_1624.MOV` 有 7 个），算进去会让帧和时间错位约 0.2 秒。
  `frames` 用 ffmpeg 输出 `rgb24` 原始帧（`-fps_mode passthrough`，可缩小），色彩标记无效时按缩略图的办法清掉标记重试。
- **显影的源图**（`engine.load_picture`）：配方用到片段时，`develop_source` 带上片段（`DevelopSource.clip(tools)`），
  解码得到那一帧或长曝光，与静态照片共用底图缓存，之后的调整、几何、缩略图、全尺寸图、导出、发送到 MapWeb 全部照旧。
  **颜色**：iPhone 片段的原色是 Display P3（`color_primaries=smpte432`），与静态照片相同，所以帧照片沿用静态照片的 ICC；
  其他片段按 sRGB。EXIF 仍从静态照片复制。帧是 1920×1440（原照片 12–24 MP），面板里会注明；片段因防抖取景比照片略窄。
- **换一帧**：显影面板的“实况”组：帧条（`GET /assets/{id}/live/strip`，10 帧拼成一张 JPEG）、原照片位置标记、
  “最清晰的一帧”（每帧灰度拉普拉斯方差，最大者；`GET /assets/{id}/live` 返回每帧时间和相对清晰度）。拖动时用 `<video>` 直接
  显示片段那一刻（不经后端），松手后保存并由后端渲染该帧（约 0.4 s），渲染结果到了再撤下视频层。
- **长曝光**（`live.blend_frames`）：先把每帧缩到 640 px 灰度，对“原照片那一帧”（没有就用中间帧）找角点，用金字塔光流跟踪到
  其他帧，RANSAC 估计相似变换（平移 + 旋转 + 缩放），这样流水、车流等运动物体不会带偏对齐；对不齐的帧不用，多数对不齐时不对齐直接叠。
  再全尺寸逐帧在**线性光**里累加（光轨亮度真实），每个像素除以覆盖它的帧数，边缘不会有黑边。结果存成 16 位 PNG
  （`renditions/<片段摘要>_lx<版本>.png`），首次约 2.5 s，之后读缓存。
- **循环 / 来回**（`live.render_motion`）：逐帧套用照片的调整（不含实况字段），P3 片段转换为 sRGB（视频和 GIF 播放器的色彩管理
  不一致；查表实现，每帧约 50 ms），由 ffmpeg 从 stdin 读原始帧编码。循环：去掉开头 0.5 秒，结尾 0.5 秒交叉淡化回开头，播放时首尾相接；
  来回：正放后倒放（不重复两端帧）。播放用的片段（长边 1080，H.264，静音）缓存为 `renditions/<片段摘要>_<效果><调整哈希>_m<版本>.mp4`，
  只随效果和调整变化，不随选的帧变化；`GET /assets/{id}/motion?effect=loop|bounce` 首次约 3 s。全尺寸图、长曝光和这些片段
  一起受 2 GB 的最近使用上限管理（`prune_full_renditions`）。
- **导出**：`ExportRequest.live_as`：`photo`（JPEG，默认）/ `video`（H.264 MP4，带效果和调整；“实况”效果带原声音）/
  `gif`（循环 GIF，15 帧/秒，默认长边 720，调色板两遍生成）。非实况照片照常导出 JPEG。MP4 只写拍摄时间，不写位置。
  实测（用户库副本）：3 段全尺寸 MP4 约 21 秒，GIF 约 7 秒。
- **显示**：列表与详情返回 `live_effect`。循环 / 来回的照片在全屏浏览里一直循环播放（左上角显示效果名），照片墙悬停 LIVE 时循环播放；
  长曝光照片当普通照片显示（标“长曝光”，不播放片段）。
- **长曝光候选**（`GET /ai/long-exposure`，整理页“长曝光候选”）：用本地 AI 的文本向量，对 8 种场景（瀑布、溪流、海浪、喷泉、
  夜晚车流、烟花、人群、流云，英文描述）各搜一次，每张实况照片取最高相似度排序；只列出片段当前能读到（不在未连接的盘上）且还不是长曝光的。
  一键“做成长曝光”即保存 `live_effect=long_exposure`。没有按画面运动量计算（需要解码上万段片段），以 AI 场景识别代替。
- **未验证**：Google 相册导出的 `.MP4` 实况片段（都在测试时未连接的 G: 盘上）；HDR（HLG / 杜比视界）的实况片段——用户库里抽查的
  都是 8 位 SDR。
